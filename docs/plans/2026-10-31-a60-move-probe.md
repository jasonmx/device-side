# A60 move probe (9d phase A0), 2026-10-31

Findings for phase A0 of `docs/plans/2026-10-30-rig-coverage-sweep.md`. Each step ran from a scratch script that held
the rig lock and opened joining on one network at a time, after checking the other two were closed.

## Auto-close check

Joining was opened for 60 s on each network in turn, with no device pairing. The script never closed a window itself
before the window plus 30 s had passed.

| Network | Opened with | Join state read from | Closed by itself |
|---|---|---|---|
| Z2M 2.14.2 | `bridge/request/permit_join` `{"time": 60}` | `bridge/info` `permit_join`, `permit_join_end` | yes, at 60.7 s |
| Hue | CLIP v2 `zigbee_device_discovery` `action_type: search` | v2 `status` (`active`, then `ready`); v1 `lights/new` `lastscan` | yes, at 56.4 s |
| ZHA | `zha.permit` `{"duration": 60}` | nowhere: no entity, WebSocket command or log line shows it | unknown; closed with `duration: 0` at 90 s |

- Hue has no call to end a search early, so its window stays open after the bulb joins, until about 56 s.
- ZHA's window is bounded by the duration in the Zigbee permit-join request, which the coordinator and routers time
  out themselves. Nothing in HA confirms it, so a script closes it with `duration: 0` as well.

## Moves

| Move | Remove | Join | Result |
|---|---|---|---|
| Z2M → Hue | `bridge/request/device/remove` (Leave); gone from Z2M in 2 s | one v2 search | joined in 14.7 s; HA entity at once |
| Hue → ZHA | v1 `DELETE /lights/<id>`, which the bridge answered `success` | `zha.permit` 120 s | **did not join in 120 s**; the bulb was left on no network |
| | Z2M touchlink fallback: `bridge/request/touchlink/scan` | | found nothing: the bulb is out of touchlink range of the Z2M coordinator |
| | Hue app: add the light, then delete it | `zha.permit` 120 s | joined in 16.8 s |
| ZHA → Z2M | `zha.remove` | `permit_join` 120 s | joined and interviewed in 11.4 s |

- **Removing a light through Hue's v1 API does not release it.** The bridge forgets the light, but the bulb keeps the
  Hue network and never looks for another. A delete from the Hue app does release it. The app's call was not
  captured; CLIP v2 `DELETE /resource/device/<id>` is the likely one, untested.
- **Touchlink can't be the fallback on this rig** unless the bulb sits within touchlink range of the Z2M coordinator.
  The Hue app's Bluetooth reset was not found in the current app.
- **Z2M's remove drops the device's Z2M options** (`hue_native_control`, `filtered_cache`, the color-mode override), so
  a move back to Z2M sets them again. Once the device is renamed back (`homeassistant_rename: true`), HA's entity
  returns under its old ID. The Hue and ZHA entities get generated IDs and need renaming to stable ones.
- Each HA entity appeared within seconds of the join, and a `light.turn_off` through it worked on every network.

## For the `--move` command

- Z2M → Hue and ZHA → Z2M can be scripted as planned.
- Hue → ZHA stays manual (delete in the Hue app, then `zha.permit`) until a probe shows v2 `DELETE device/<id>`
  releases the bulb.
- Every join window can be finite, and all three networks close once the bulb is in, or on their own timers. A ZHA
  window must still be closed explicitly, because nothing confirms it closed.
