# Slice 7: Hue port

## Context

hue_dimmer (`../hue-smooth-dimming`, source of truth: branch `origin/release/v0.5.1rc1`; its Python and tests
match the checkout) gets ported into device_side as Hue adapters, so device_side can later replace it. The repo
plan (`docs/plans/2026-10-23-device-side-repo-plan.md`: Scope `move` design, "Hue port" mapping, Concurrency,
open items 10 and 12) already fixes the action contracts; this plan records the interview decisions it left
open and the delivery order.

Core already has what the port needs (`IntegrationInfo.is_group/expand_group`, `AdapterScope.native_groups`,
`EntityResult.data`, `DeviceSideData.integration_state`, `hue` in `after_dependencies`, rig step examples for
all four actions). Missing: a `hue` package, query-action plumbing (`SupportsResponse.ONLY`), aiohue in tests.

## Decisions (interview 2026-10-25)

- **Three PRs**, each its own worktree (`wt/hue-<topic>` off `release/v0.0.2`), audit and rig run: 7a, 7b, 7c below (7d dropped).
- **Zones follow Hue's own pattern** (Hue room/zone = one HA light backed by `grouped_light`):
  - *Reads:* `get_attributes` on a zone returns the zone's row plus one row per member. Zone row: brightness
    = the bridge's `grouped_light.dimming.brightness` (average of members that are on); color temp and xy =
    HA's rule (average over members that are on, `hue/v2/group.py`). All members off (the bridge reports
    nothing useful): average over all members, as hue_dimmer does.
  - *Moves:* brightness and color temp go to the zone as one write (absolute target + `dynamics.duration`);
    members converge on the target together, as hue_dimmer's `raise` does. Duration comes from the zone's
    current value. **Saturation goes to each member** (a single zone xy would turn every bulb the same color).
  - *Writes:* `set_attributes` and `set_scene` expand to members (per-light writes apply while off), as today.
- **`move` covers brightness, color temp and saturation** in slice 7. `hue` direction stays `unsupported` on Hue.
- **Ramp API is `move` + `stop`, nothing else** (debated 2026-10-25). No dedicated dim/brighten actions: adding
  them later is cheap, removing them isn't, and one action lets a hold-to-dim blueprint template the direction.
  Discoverability goes in the translated name (e.g. "Move: dim, brighten, warm or cool"), which can change
  after release. If testers can't find or fill `move` for hold-to-dim, add `start_dimming`/`start_brightening`
  as wrappers whose `Action.run` dispatches to the `move` adapters (no new adapters or bench records).
- **Brightness directions are `up | down`** (debated 2026-10-25), replacing `brighter | dimmer`. `dimmer` is
  also the hardware's name and invites `brightness: !input dimmer` mix-ups in blueprints; `darker` reads as a
  color change ("a darker red"), overlapping `saturation: richer` silently, while a wrong `color_temp: up`
  guess is refused loudly. For the many non-native readers (raw values are English in YAML, blueprints and
  LLM calls; only UI labels translate), `up`/`down` are first-lesson words, and the color sense of "darker"
  carries into other languages (dunkelrot, bleu foncé). **`saturation` is `up | down` too** (replacing
  `richer | paler`). Rule: `up | down` wherever the direction is unambiguous. `color_temp` stays `warmer | cooler`:
  Z2M's `color_temp_move: up` means warmer (mireds), HA's old `color_temp` field was mireds, and in everyday
  speech "temperature up" means warmer while physics says higher K is cooler-looking. **`hue` is `up | down`
  too** (replacing `forward | backward`): `up` = the `hs_color` hue angle increases (red → yellow → green),
  wrapping at 360°; `forward` hid a clockwise/counterclockwise assumption. So every direction field is
  `up | down` except `color_temp: warmer | cooler`. 7b updates the repo plan's `move` bullet (directions and
  the rule) and `tests/rig/steps/examples/move.yaml` to match.
- **Port as-is:** no gamut clamp on `set_attributes`, no `set_scene` throttling, no move/stop locking. File one
  issue each (with fix shape and agent model, per the global rule). Saturation still reads the bulb's gamut
  for its end point: that is new behavior, not a fix.
- **Keep `min_brightness` and `max_brightness`** on `set_attributes`.
- **All Hue adapters ship `experimental=True`** (new integration). Dropping the flag is a separate maintainer call.
- **Rig:** the bridge has color-temp bulbs paired now; the color bulb arrives 2026-10-26. Color steps
  (`set_attributes` color, saturation `move`, xy reads) wait for it; everything else runs now.

## Delivery

  is_group=<is_hue_group attr>, expand_group=<grouped_light.get_lights -> member Targets>, max_concurrency=2)`.
- `integrations/hue/bridge.py`: port of hue_dimmer `bridge.py` taking a `Target`; `entry.runtime_data` is the
  `HueBridge`, `api_version < 2` -> `supports()` returns `bridge_v1`; `_write_light` raises (adapter emits
  SENT/REJECTED) instead of logging.
- `integrations/hue/colors.py`: port of `attributes.py` (xy/hs/rgb resolution, kelvin clamp, mirek).
- Adapters `set_attributes.py`, `get_attributes.py` (`native_groups=True`: builds the zone row from the

  mixed modes). ≥95% line coverage per adapter module.
- Rig: add `hue` entries to the main checkout's `inventory.yaml` (roles `light_ct`, `group`, `scene`;
  `light_color` once the bulb is paired); promote `steps/examples/{set_attributes,get_attributes,set_scene}.yaml`
  into `steps/`, color steps `only:` the color role. Bench records via `scripts/rig.py`.
- `docs/integrations.md` Hue section.

### 7b: move/stop for brightness (hue_dimmer parity)

- `integrations/hue/transition_cache.py`: `TransitionCache` in `integration_state["hue"]`, keyed by
  (resource_id, attribute); entry = start value, target, duration, started_at; interpolate on read; 15 s
  settle guard (`API_SETTLE_SECONDS`); write only after the bridge accepts (hue_dimmer's "phantom transition"
  rule). `get_attributes` reads through it (checklist §4 mid-transition prediction).
- Actions `move.py` (fields per the repo plan: per-attribute directions, `sweep_time` default 5, collapsed
  "Limits" section; at least one direction required) and `stop.py` (no fields).
- Adapters `move.py` / `stop.py` with `native_groups=True`. Brightness: `dimming` target + `dynamics.duration`
  = sweep_time × fraction left; up sets `on: true`; `detail: at_limit` when already there. Down to 0 % is
  a plain soft off: `on: false` + duration, no `dimming` (brightness 0 would make the next plain on come back
  at the minimum). Stop: `dimming_delta` stop, then cache the interpolated value; during our own soft off,
  `on: true` + the interpolated brightness, no duration (the bridge refuses a dimming stop there; measured on a
  single light, so a room is cut light by light, each at its own prediction). A soft off
  device_side didn't start can't be predicted: `stop` returns a clear result instead of the bridge's refusal.
- Move up from off starts at 0 %, as in hue_dimmer, and the cache predicts from 0 %. After a plain soft off the
  bridge keeps the old brightness, which `on: true` + target + duration might jump to first (unmeasured). If the
  rig shows a jump, the move-up write carries a starting brightness (0 % with no duration first, or the
  minimum in the same write); the soft off stays plain.
- Port `test_core.py`, `test_transition_errors.py`. Rig: promote `steps/examples/move.yaml` (§2 on
  `light_ct` and `group`). Verify `sections:` with `collapsed: true` passes hassfest (open item 12).
- End-value spike (`docs/plans/2026-10-26-hue-echo-spike.md`, Result) decided with Jason 2026-10-26:
  - The timer cache stays for now. The `observe()` design is dropped: late bulb reports can land mid-ramp, so
    "any event that isn't our end value is real" fails. A replacement is argued in a fresh session.
  - `stop` on a light dimming to off is refused by the bridge ("soft off"). A move's soft off must always be
    stoppable: handled as in the adapter bullet above, rather than with a device_side timer that sends the
    off, which would fail if HA restarted mid-ramp. Users who want an unstoppable fade use HA's `turn_off`.
  - The option layer (hide our end value, emit predicted values) gets its own plan, off by default, covering
    brightness and `on`: it hides the soft off's early `on: false` and emits off when the ramp ends, so HA shows
    the light on until it reaches zero. With the option off, HA shows off from the start. The layer must tell a
    mid-ramp bulb report (`on: true` at 17 % in 1 of 2 runs) from a real change, and pass an off made elsewhere
    during the ramp straight through.

### 7c: move for color temp and saturation

- Color temp: `color_temperature.mirek` target (limit or the light's/zone's range end) + duration; one zone
  write for zones. Stop: `color_temperature_delta` stop.
- Saturation: per member (dispatcher expansion for this attribute: the adapter expands a zone itself via
  `expand_group` when only saturation is moving, or splits a combined call). End point on the line from the
  white point through the current xy to the bulb's gamut edge (`light.color.gamut`); `saturation_limit` is
  the fraction along that line; paler -> toward the white point. Stop: write the interpolated xy, duration 0.
- Rig answers open item 12 first: whether a `color_temperature` dynamic on a zone works, and whether separate
  brightness and color-temp writes run independently. If not, one write with the longest duration and
  `detail: shared_duration`. Record the answer in the repo plan's open item 12. The end-value spike showed a
  `color_temperature` dynamic on a zone works; whether the two writes run independently is still open.
- Rig: color-temp steps now; saturation steps once the color bulb is paired.
